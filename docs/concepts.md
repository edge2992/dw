# Discussion Workspace (dw)

## The core idea

トピックごとに議論用のディレクトリを切る。会話は毎回新しく始まるが、**そのトピックについて分かっていること**は引き継がれる。

引き継ぐのは会話ログではない。会話の要約でもない。**状態としての知識**——前提、却下した案、未決の問い。これらは切り口に依存しないので、前回と違う角度から入っても有効に働く。

セッション継続（`--continue`）との違いがここにある。継続は会話の流れごと引き継ぐので、前回の路線に引き戻される。dw は流れを捨てて土台だけ残す。だから毎回新しい切り口で入れる。

そしてディレクトリは保管場所ではなく、**議論のための作業場**。資料を集め、構造を作り、その状態を文脈として議論する。

---

## Architecture

四つの層がある。

**Sources** — そのトピックのために集めた資料。設計書、ログ、仕様、抜粋、他のリポジトリから持ってきたファイル。この層は不変で、LLM は読むだけで書き換えない。何を集めたかがそのままコンテキストの範囲になるので、**ここに何を置くかが議論の射程を決める**。

**State** — トピックについて分かっていることを保持する一枚のドキュメント。前提、却下した案とその理由、未決の問い。会話ではなく状態を記述する層で、**会話の回数に依存しない**のが要点。何回議論しても分量は増えず、上書きされていく。ここだけが次のセッションに引き継がれ、他はすべて揮発する。人間が読む場所でもあり、LLM が最初に読む場所でもある——両者が同じものを読むので二重管理が起きない。この層は原則として人間が所有する。書く行為そのものが思考であり、自動生成に委ねるとトピックの理解ではなく会話の要約に退化する。

**Working area** — 議論の過程で生まれるもの。生成されたコード、比較表、検討中の下書き、セッションログ。捨ててよい層で、次回に引き継がれない。ここが独立していることで、State を汚さずに試せる。

**Convention** — dw をどう扱うかを LLM に伝えるドキュメント（`CLAUDE.md`）。どの層が読み取り専用か、State に何を書き何を書かないか、閉じるときに何をするか。三層の分離は物理的には保証されないので、**規約として明示して初めて成立する**。他の層と違い、トピックではなく dw というパターンそのものに属し、使いながら育つ。

この分離は**書き手**による。外部が書いたもの、自分が書いたもの、LLM が書いたもの。混ざると、時間が経ったときに「どれが信頼できる情報か」が判別できなくなる。分類のためではなく、信頼性の識別のための分離。

そして層の外に、境界そのものがある。

**Isolation** — トピック単位でディレクトリが閉じていること。他のトピックの文脈が混入せず、資料は共有せずにコピーする。二重管理のコストより、コンテキストの範囲が明確であることが勝つ。継続性はセッションの継続からではなく、この境界と State の二つから生まれる。

## Operations

**開く** — `dw <topic>`。State を読んだ状態でセッションが立つ。継続はモードではなくデフォルトの挙動。

**資料を入れる** — Sources にコピーする。他の dw と共有したくてもリンクしない。URL のままにせず抜粋して置く——次に開いたときリンク切れか、内容が変わっている。ファイル名から復元できない情報だけを添える：出所、置いた理由、そして**もう見なくていいもの**。検討済みの資料が残っていると、LLM は毎回それを読む。

**議論する** — Working area で試す。State には触らない。

**閉じる** — LLM にログの追記と、State 更新の**差分案**を書かせる。確定は手でやる。却下は条件付きで書く——「案 X は駄目、理由は Y、Y が崩れたら再検討」。却下は永久ではない。

**一覧** — 引数なしの `dw`。各 State の見出しと未決の先頭行を並べる。索引を別に持たない。

**時間を空けて戻ってくる** — 数週間ぶりに同じトピックを開いたとき、State に書かれた結論は当時の前提の上に立っている。状況が変わっていても、そのまま読めば正しく見えてしまう。前提を「事実」と「判断」に分けて日付を添えておくと、古い行が目に入った時点で、まず疑うべき場所が分かる。

**規約を育てる** — 共通の規約は dw 全体で一つ。トピック固有の指示は各 dw に置き、共通側に混ぜない。固有の指示が増えてきたら、State に書くべき内容が紛れ込んでいる可能性がある。**規約は振る舞いを書き、State は内容を書く**。

## Tips and tricks

**シェル側で完結させる。** `dw` を関数として `.zshrc` に置けば、`cd` してセッションを立てるまでを一手で済ませられる。ディレクトリ移動を伴うので、実体はバイナリではなくシェル関数のほうが扱いやすい。

**fzf で選ぶ。** トピックが増えると名前を覚えていられない。引数なしの `dw` を `fzf` に流し、State の先頭数行を preview に出すと、選ぶ前に中身が見える。補完を書くより手軽で、結果的に一覧と検索を兼ねる。

**横断検索は `rg`。** 却下した案を探すときは、ディレクトリを跨いで State だけを対象に引く。Working area を除外するのがコツ。

**移動は薄いエイリアスで。** dw の中に入って普通に作業したいことも多いので、セッションを立てずに `cd` だけする経路を別に持っておく。

道具はこの程度でいい。凝ると、dw そのものが手入れの対象になる。

## Why this works

**State が唯一の入口だから、二重管理が起きない。** 人間が読むものと LLM が読むものが同じ。片方だけ更新される事故がない。ツールを介さず、エディタでも GitHub でも読める。

**状態が会話回数に依存しないから、肥大しない。** 要約の要約を重ねると劣化するが、状態の上書きは劣化しない。10 回議論しても読み込み量は変わらない。

**却下の記録が、切り口をまたいで効く。** 角度を変えて入ると、LLM は同じ案を新鮮な顔で提案してくる。ここが残っていないと毎回潰す羽目になる。会話要約から真っ先に落ちるのもここなので、明示的な枠が要る。

**Isolation が、コンテキストの制御そのものになる。** 何を読ませるかを、ファイルをどこに置くかで決められる。プロジェクト間の混入も同時に防げる。

**議論の成果がファイルとして残る。** ブラウザのチャットは読み返せても、取り出すには手作業がいる。

## Note

**土台を渡すことは、前回のフレーミングを渡すこと。** 「前提」に書かれているものが、実は前回の切り口から見たときだけの前提だった、というのは起きる。切り口を変えて入る使い方をするほど効いてくる。日付と、事実／判断の分離はその対処だが、完全には防げない。

**反論の独立性には限界がある。** 命題も反論も同じフレーミングから生成されるので、出せるのは「その枠から到達可能な範囲の反論」に閉じる。納得感のある反論が出たときほど、枠の外は静かなまま残る。自分の結論を先に渡さない、といった順序の工夫で緩和はできるが、消えはしない。

**dw は思考法ではない。** Goal→観点→調査→まとめのような型を強制する仕組みではなく、トピックごとに文脈を保つ入れ物にすぎない。型は必要なときに State に書けばよく、ツールに埋め込むものではない。

**効いているかの判定。** 閉じるときに「考えが変わったか」を 1 行。全部「変わらなかった」なら、それは体裁のいい日記になっている。
